# Software Requirements Specification — Phase 0–1 Modules

Requirement analysis as specified in BRD §17 ("Second"). Each module is analyzed here before it is built. Later modules are added when they are approved.

---

## 1. Identity & Access

| Aspect | Specification |
|---|---|
| Objective | Secure login and configurable, permission-based access for every user |
| Actors | Super Administrator (manage), Hospital Admin (view), all users (login, change password) |
| Functions | Login (username or email), refresh, logout, change password, forced change on first login; user CRUD, activate/deactivate, admin password reset; role CRUD; assign roles to users; assign permissions to roles; direct user permissions; login history |
| Business rules | Usernames and emails are unique (case-insensitive). The Super Administrator role cannot be deleted, and its last active member cannot be deactivated. Users cannot deactivate themselves. Deactivating a user or resetting their password revokes all of their refresh tokens. Permissions are synced from code and cannot be created by users. |
| Validation | Password policy (Q-SEC-2); email format; phone up to 20 characters; role name 2–100 characters |
| Exceptions | Locked account returns 401 with a lockout message. Inactive user returns 401. A reused refresh token revokes its token family and returns 401. |
| Audit | Login success and failure, user create/update/status change, role and permission changes, password resets |
| Acceptance | Unauthenticated calls return 401. A user without permission gets 403 on every protected endpoint. Revoking a permission takes effect on the next request. Lockout works. The seed Super Admin is created from environment variables. |

## 2. Audit

| Aspect | Specification |
|---|---|
| Objective | Immutable trace of important actions (BRD §6.4, TAD §14) |
| Actors | System (writer); Super Administrator (reader) |
| Functions | Automatic entity-change capture for `[Audited]` entities; explicit business-event records; paged, filterable viewer (date range, user, module, entity, entity ID) |
| Rules | No update or delete path. Sensitive fields (password hashes, tokens) are never captured. Audit rows commit atomically with the change. |
| Acceptance | Creating or updating a patient produces an audit row with old and new values. The viewer requires `Audit.View`. |

## 3. Administration

| Aspect | Specification |
|---|---|
| Objective | Hospital profile and organizational configuration used by all modules |
| Functions | Hospital profile (single record, logo upload); departments with optional parent; designations with category; number sequences (view/edit prefix and format, never decrease the current value); settings (timezone, currency, financial-year start) |
| Rules | Department code and name are unique. A department with active children or referencing employees cannot be deactivated (checked through `IEmployeeLookup`). Departments are deactivated, never hard-deleted. |
| Contracts provided | `IDepartmentLookup`, `IHospitalSettings`, `INumberSequenceService.NextAsync(key)` |
| Acceptance | The MR sequence produces unique, gap-tolerant numbers under concurrent registrations. Profile changes are audited. |

## 4. HR — Basic Employee

| Aspect | Specification |
|---|---|
| Objective | Basic employee register (BRD Phase 1) so users, doctors and nurses can be linked to departments |
| Functions | Employee CRUD, search, status change; link an Identity user to an employee |
| Rules | Employee code is unique (auto-generated through a number sequence, or manual: *to be confirmed*). The department and designation must exist and be active. |
| Out of scope (P7) | Attendance, leave, shifts, payroll, documents, salary |

## 5. Patient (reference module)

| Aspect | Specification |
|---|---|
| Objective | One permanent record per patient, and fast search (BRD Module 02) |
| Actors | Receptionist (register, update, request merge); Doctor and Nurse (view, medical info); Hospital Admin (approve merge, deactivate) |
| Inputs | See DATABASE-DESIGN §7. Mandatory fields are listed in Q-PAT-2. |
| Functions | Register; search (MR number, mobile, name with fuzzy matching, ID number); profile; update demographics; duplicate candidates; merge request and approval; deactivate/reactivate; allergies CRUD (status-based, no hard delete); medical history; documents upload, download and delete (permission-controlled); ID card PDF |
| Business rules | One permanent MR number, generated by the server and never editable. Duplicate warnings follow Q-PAT-4. A merged record becomes read-only. Allergies are marked "Entered in error" rather than deleted. Every view of the medical-info tab is audited. |
| Outputs | Patient profile DTO; patient summary contract `IPatientLookup` for other modules; ID card PDF |
| Exceptions | An exact duplicate ID number returns 409. Updating a merged or inactive patient returns 422. A stale `rowVersion` returns 409. |
| Acceptance | BRD §15 items 3–4: registration and search work. Duplicate control works. Concurrent registrations never produce duplicate MR numbers. Search on 100k patients returns in under 1 s. |
